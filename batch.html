BATCH: one command, many Claude agents

Free cheat sheet from Gelbi AI. Keyword: BATCH.

How to read this page:

  • DOC = stated in the official Claude Code docs. The source URL is on the line.
  • SUGGESTION = my idea. It is not from the docs. Try it, do not treat it as a documented fact.

Docs checked: 2026-11-11 and 2026-11-12. Re-check a detail before you rely on it.

1. What it is

  • DOC /batch <instruction> is a bundled skill: "Orchestrate large-scale changes across a codebase in parallel." Bundled skills are prompt-based: they give Claude detailed instructions and let it orchestrate the work with its tools.
    https://code.claude.com/docs/en/commands and https://code.claude.com/docs/en/skills
  • DOC "Up to thirty agents" in the video is derived: one subagent per unit, and the docs say 5 to 30 units.

2. The exact steps

  1. DOC Be in a git repository. Or have a WorktreeCreate hook that creates the worktrees. Outside a git repo, /batch needs Claude Code v2.1.281 or later.
    https://code.claude.com/docs/en/worktrees#non-git-version-control
  2. DOC Type /batch and an instruction. The docs example: /batch migrate src/ from JavaScript to TypeScript
  3. DOC Claude researches the codebase, decomposes the work into 5 to 30 independent units, and presents a plan.
  4. You read the plan and approve it. DOC Nothing is spawned until you approve.
  5. DOC It spawns one background subagent per unit, each in an isolated git worktree.
  6. DOC Each subagent implements its unit, runs tests, and opens a pull request, or reports what happened.
  7. DOC To check on the background work, run /tasks. It lists background work in the current session, including subagents that have finished.
    https://code.claude.com/docs/en/commands

Steps 2 to 6: https://code.claude.com/docs/en/commands (row for /batch)

3. Prompt pack (all SUGGESTION)

The docs give one example instruction. These follow the same shape. Replace the placeholders with your own names.

  1. /batch migrate src/ from JavaScript to TypeScript (the docs example)
  2. /batch replace every call to <oldFunction> with <newFunction>, update the tests that use it
  3. /batch add input validation to every handler in src/api/, one handler per unit, each unit must pass npm test
  4. /batch convert every class component in src/components/ to a function component
  5. /batch update imports after I moved src/utils/ to src/lib/

Tips, all my own suggestions:

  • Say how each unit is judged done (a test command that must pass).
  • Say what is out of scope (for example "do not touch src/legacy/").
  • Prefer changes that are repeated mechanically and do not depend on each other. The docs say the work is split into independent units.
  • Read the plan carefully before you approve. Check that no two units edit the same file.
  • Read each pull request yourself. The docs say each agent opens a PR or reports what happened. They do not say anything is merged for you.

4. The 10 best use cases (all SUGGESTION, each fits "a change that spans the codebase, split into independent units")

  1. JavaScript to TypeScript migration (the docs example).
  2. Replace a deprecated API across every call site.
  3. Rename something used in many files, when the files can be updated separately.
  4. Move to a new import path after you restructure folders.
  5. Move a test suite to another framework, file by file.
  6. Upgrade a library whose API changed, package by package.
  7. Class components to function components.
  8. Move hard-coded strings into a translation layer, component by component.
  9. Add missing type hints or docstrings, module by module.
  10. Add tests for modules that have none, one module per unit.

5. Extra things you can do

  • DOC Run it outside git. A WorktreeCreate hook lets you run /batch outside a git repository (for example SVN or Perforce). Each subagent then publishes its change with your project's version-control commands, and reports what it published if it cannot open a PR.
    https://code.claude.com/docs/en/worktrees#non-git-version-control
  • DOC Copy local files into each worktree. A .worktreeinclude file (.gitignore syntax) copies gitignored files, such as .env, into every new worktree, including subagent worktrees.
    https://code.claude.com/docs/en/worktrees (section on .worktreeinclude)
  • DOC Mind the base branch. New worktrees branch from the repository's default branch on the remote by default. If your in-progress work is on another branch, set worktree.baseRef to "head" so worktrees start from your local HEAD.
    https://code.claude.com/docs/en/worktrees#choose-the-base-branch
  • DOC Cleanup. A subagent worktree with no changes is removed automatically. One with changes stays on disk until a periodic sweep can remove it without losing work.
    https://code.claude.com/docs/en/worktrees (section on subagent worktrees)
  • DOC One isolated session, no fan-out. claude --worktree <name> starts a single session in its own worktree.
    https://code.claude.com/docs/en/worktrees
  • DOC Keep one session running toward a finish line. /goal <condition> keeps Claude working across turns until the condition is met.
    https://code.claude.com/docs/en/goal

6. What the docs do not tell you

Do not assume any of these. The docs I checked do not state them:

  • how fast a run is, how much it costs, or how many agents run at the same time
  • that the pull requests are correct, or that they are merged for you
  • which plan or model you need

Watch your own usage, and review everything before you merge.
